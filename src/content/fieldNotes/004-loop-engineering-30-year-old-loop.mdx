On June 7, 2026, Peter Steinberger [posted two sentences](https://x.com/steipete/status/2063697162748260627): you should not be prompting coding agents anymore, you should be designing loops that prompt your agents. The post did 8.4 million views. It contained no definition, no building blocks, and no specification. The field spent the following week supplying all three. Addy Osmani's [essay](https://addyosmani.com/blog/loop-engineering/) gave it the canonical line, loop engineering is replacing yourself as the person who prompts the agent, and the lineage was complete: prompt engineering, then context engineering, then harness engineering, and now, the fourth floor, loop engineering.

That can read as if loop engineering is nothing, and that is the mistake to avoid. The new part is real. It is not the loop; it is the orchestration around it. You stop prompting turn by turn and build the system that runs the agent for you: schedules and automations that start it, git worktrees so several runs proceed at once, maker-checker sub-agents that grade each other, reusable skills, and durable state that outlives a crash. The human leaves the prompting seat, and that is a real change in how the work gets done. What is not new is the thing the orchestration drives. The loop at the center, the part that decides what to do and when to stop, is thirty years old; the new layer is built straight onto its two oldest unsolved problems, and it ships without an answer to the question an incident review asks first. The hashtag is new. The hard parts are not.

## The claim, steelmanned

Take the strongest version first, because the practice is real and worth describing. Instead of typing each instruction, you stand up an orchestration layer: automations and schedules that start the agent, git worktrees so several runs proceed in parallel without colliding, sub-agents in a maker-checker arrangement where one writes and another reviews, reusable skills and plugins, and durable state so a run can be paused, resumed, and audited. Osmani's line for it is exact: you replace yourself as the person who prompts the agent. Holding the agent like a tool becomes running it like a process. That orchestration is genuine engineering, and naming it is fair.

What the name quietly absorbs is the thing the orchestration drives. Underneath every schedule and every sub-agent is still a loop deciding what happens next: a goal, an action, a check on the result, an update to state, and a decision to continue, retry, stop, or escalate. The orchestration that wraps it is new. That decision loop is not, and we can date it precisely.

## The decision loop is old, and so is its hardest problem

In 1995, Rao and Georgeff published the [BDI agent architecture](https://cdn.aaai.org/ICMAS/1995/ICMAS95-042.pdf) with a concrete "main interpreter loop": initialize, then repeat, generate options, deliberate, update intentions, execute, take in new events, drop the goals that are now achieved or impossible. Take away the language model and the scheduler and that is the loop your orchestration is driving today, down to the step where it decides which goals to abandon. The layer around it is genuinely new. The decision procedure at its center is not.

And the question loop engineering treats as a fresh frontier, when to stop and when to reconsider, is the oldest problem in that loop. Rao and Georgeff named it in 1995 and called it the horns of a dilemma. Reconsider your plan at every step and you pay a deliberation cost so high the action may be stale by the time you commit. Commit unconditionally and you keep marching after the goal has become unreachable. Their fix was not a solution; it was to bound how often you reconsider, and even that they credited to a 1991 paper. Thirty years and a literature later, it is still open. Loop engineering automates the machinery around that decision and leaves the decision itself exactly where it found it.

The line continues unbroken. [ReAct, in 2022,](https://arxiv.org/abs/2210.03629) interleaved a reasoning step and an acting step into the thought-action-observation cycle every modern agent runs, three and a half years before the term. [Reflexion](https://proceedings.neurips.cc/paper_files/paper/2023/file/1b44b878bb782e6954cd888628510e90-Paper-Conference.pdf), the canonical self-reflecting agent loop, landed at NeurIPS in 2023. And here is the detail that matters: Reflexion was not unbounded autonomy. It was hard-capped by a maximum trial count and by a memory of one to three stored experiences, truncated to fit the context window. Its stop was external, an evaluator's pass-or-fail or the trial limit, never the agent's own say-so. A celebrated self-reflecting loop only worked because someone put a fence around it. That is the part the 2026 framing leaves out.

## The part it quietly hands back to you

This is where it stops being harmless. The orchestration's own answer to when the loop stops is the maker-checker: a second agent checks the first agent's work, and that check is the stop condition. Osmani is honest about why you need it: the model that wrote the code is too nice grading its own homework. He is right that you need an external check. The discourse is wrong about how hard that is, and about whether a model can be the check at all.

The evidence is not ambiguous. Models cannot reliably find their own reasoning errors. On a [benchmark built for exactly this](https://arxiv.org/abs/2311.08516), GPT-4 identified mistakes at 52.87 percent, which on a near-binary task is a coin flip; GPT-3.5 managed 14.78 percent, against human raters who agreed with each other above 97 percent. And without an external signal, asking a model to review its own answer does not just fail to help, it actively hurts: a [DeepMind team found](https://arxiv.org/abs/2310.01798) intrinsic self-correction dropped GPT-4 from 95.5 to 91.5 percent on grade-school math, because the model talks itself out of correct answers as readily as wrong ones. The reported successes in the literature quietly used the ground-truth label to decide when to stop. Take the oracle away and the loop has no reliable way to know it is done. Even the agent's own unit tests are unsound as a gate: Reflexion's authors measured a 16.3 percent false-positive rate on one benchmark, which means a loop can pass every test it wrote for itself and still be wrong.

So the verifier is not a component you bolt on at the end. It is the whole problem, and the discourse's own slogan, the verifier is the bottleneck, is more true than the people repeating it seem to realize. A loop with a self-graded stop condition is not autonomy. It is a confident machine with no brakes.

There is a constructive way out, and it is worth stating because it tells you what to actually build. The same research that shows models cannot find their own errors shows they can fix errors once the location is supplied from outside: given the mistake's position by an external checker, the backtracking method recovered 43.92 percent of previously wrong answers while losing under 7 percent of the right ones. The fixing capability is real. The self-detection is not. That asymmetry is the design rule. The verifier must be external to the maker. A code executor, a type checker, a test suite the agent did not author, a schema validator, a second model with a different objective and no stake in the first one's answer. Ground the stop in something the loop cannot talk itself past, or do not run it unattended.

## The sentence nobody in the discourse writes

The loop-engineering conversation reaches the edge of the real problem and stops. Osmani gets one sentence from it: a loop running unattended is also a loop making mistakes unattended. True. But that sentence is about correctness, and the next sentence, the one nobody writes, is about authority.

A loop that runs while you sleep, holds a broad production credential, and stops only when it decides it is finished is not a productivity pattern. It is the exact architecture that deleted a production database in nine seconds this past April, after a coding agent reached for an unscoped credential and ran a destructive call against production, and the one that wiped a database under an explicit code freeze the previous July. I traced both of those incidents in detail [elsewhere](https://sunilprakash.com/writing/the-same-database-twice/). The shape is always the same: the credential was wider than the task, and the stop was a sentence the model agreed to rather than a gate the system enforced. Loop engineering, as it is being evangelized, is that shape with better branding and a scheduler attached.

This is the gap the discourse leaves open. The guides talk about verification at length and almost never about blast radius. They do not ask the question an incident review asks first: when this loop acts against something that matters, what is it allowed to touch, and who can prove afterward that it was allowed. The stop condition the evidence says the model cannot self-enforce is the same boundary that, left to a prompt, ends with a destroyed database. The answer is not a better prompt. It is authority that is scoped and enforced outside the model: a credential narrowed to the task, a destructive action the agent cannot call without an out-of-band approval it does not hold, a verifiable record of who delegated what. The boundary is something you can say in a sentence: this run may edit docs but not reach production credentials, it may open a pull request but not merge it. That is the layer an open protocol like AIP exists to provide: a verifiable agent identity whose authority can only narrow as it passes down a chain of delegations, enforced outside the model. It is the missing floor under everything the loop discourse is excited about. Build the loop all you want. Put an enforced gate between it and anything you cannot undo.

<PullQuote>The stop condition is the whole problem, and it is the one decision the model cannot be trusted to make about itself.</PullQuote>

## Where this fails

Two honest limits. First, this is not an argument against loops. Loops grounded in external verification, a code executor, a test harness, a compiler, genuinely work, and they are how the best agent systems ship today. The target here is the prompted stop and the self-graded check, not the practice of designing the loop. Second, the reliability numbers have a clock on them. [METR measured](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/) that in early 2025, frontier agents reliably handled only a few minutes of expert work, with a fifty-percent success horizon near an hour, which on its face undercuts "runs while you sleep." But that horizon has been doubling roughly every seven months, so by the time you read this it is longer, and METR itself cautions that the metric is not a literal measure of how long an agent can run alone. The point that survives the caveats is the direction, not the number: reliability decays as the chain of actions grows, and the longer a loop runs unattended the more certain it is to need a brake it cannot supply itself.

And naming things has value. Loop engineering names a real layer, the orchestration that takes you out of the prompting seat. The failure is not the name. It is shipping that layer on top of two unsolved problems, the stop condition and the verifier, and an ungoverned blast radius, while presenting all three as details. The name is not the issue. The amnesia is.

## In code

The companion code is the whole argument, in two forms. First a deterministic version you can read in a sitting: one loop, run two ways. In the first the agent decides when it is done and the destructive step is a normal function call; in the second the same loop runs against three external fences, an iteration cap, a no-progress detector that hashes each call and halts on a repeat, and a destructive action that cannot execute without an approval the agent never holds. One can delete the database on a hallucinated "done." The other cannot, by construction.

Then the same contrast with a real LLM agent on LangGraph, because the abstraction is easy to wave away and a running agent is not. Told to clean up a staging table, the ungated agent reaches for the destructive tool and nothing stops it; the enforced agent runs the identical model and tools, but the destructive call is gated and the loop is capped, so it cannot delete whatever it decides. The brake is not in the prompt and not in the model. It is the layer the orchestration is missing. You can run the contrast in the browser on [the Bench](/bench/).
