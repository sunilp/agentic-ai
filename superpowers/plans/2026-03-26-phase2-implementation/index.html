    Task 3: Multi-Agent Code -- Contracts, Agents, Orchestrator¶

    Files: - Create: src/ch04_multiagent/__init__.py - Create: src/ch04_multiagent/contracts.py - Create: src/ch04_multiagent/agents.py - Create: src/ch04_multiagent/orchestrator.py - Create: src/ch04_multiagent/compare.py - Create: src/ch04_multiagent/run.py - Test: tests/unit/test_contracts.py - Test: tests/unit/test_orchestrator.py - Test: tests/integration/test_multiagent_pipeline.py

    The multi-agent system extends the Document Intelligence Agent with role decomposition: - RetrieverAgent: searches and retrieves relevant document chunks - ReasoningAgent: synthesizes an answer from evidence with citations - VerifierAgent: checks that citations are actually supported by the retrieved text

    The orchestrator coordinates: retrieve -> reason -> verify -> return (or loop if verification fails).

    Implementation guidance:

    contracts.py defines the message types agents exchange: - AgentMessage(sender, recipient, content, message_type, metadata) -- base message - RetrievalRequest/RetrievalResult -- retriever agent messages - ReasoningRequest/ReasoningResult -- reasoning agent messages - VerificationRequest/VerificationResult -- verifier agent messages - Message types: TASK, RESULT, FEEDBACK, ESCALATION

    agents.py defines three role-based agents, each with: - A role-specific system prompt - A run(message: AgentMessage) -> AgentMessage interface - The RetrieverAgent uses DocumentIndex to search - The ReasoningAgent uses ModelClient to generate answers from evidence - The VerifierAgent checks each citation against source text

    orchestrator.py implements MultiAgentOrchestrator: - Takes a query, dispatches to agents in sequence - Handles the verify -> re-reason loop (max 2 verification rounds) - Tracks total tokens, latency, and step count across all agents - Returns an AgentResponse (same type as single-agent, for comparison)

    compare.py implements MultiAgentComparisonRunner: - Runs both single-agent (from src/ch03/agent.py) and multi-agent on the same queries - Prints side-by-side comparison: steps, tokens, latency, confidence, answer quality

    Tests should verify: - Message contract creation and serialization - Orchestrator dispatches in correct order - Verification failure triggers re-reasoning - Full pipeline returns cited answer (integration test with MockClient)

    • [ ] Step 1: Write contracts.py

    Define all message types as Pydantic models. Include sender/recipient fields, message_type enum, and typed payload models for each agent pair.

    • [ ] Step 2: Write tests for contracts

    Test message creation, serialization, and that all required fields are present.

    • [ ] Step 3: Write agents.py

    Three agent classes (RetrieverAgent, ReasoningAgent, VerifierAgent), each implementing async def run(message: AgentMessage) -> AgentMessage. Each has a focused system prompt for its role.

    • [ ] Step 4: Write orchestrator.py

    MultiAgentOrchestrator with async def run(query: str) -> AgentResponse. Coordinates the three agents. Handles verification loops. Tracks cumulative usage.

    • [ ] Step 5: Write orchestrator tests

    Test dispatch order, verification loop behavior, budget exhaustion.

    • [ ] Step 6: Write compare.py and run.py

    Comparison runner and CLI entry point.

    • [ ] Step 7: Write integration test

    Full pipeline with MockClient: query -> retrieve -> reason -> verify -> answer.

    Files: - Create: src/ch05_hitl/__init__.py - Create: src/ch05_hitl/approval.py - Create: src/ch05_hitl/escalation.py - Create: src/ch05_hitl/audit.py - Test: tests/unit/test_approval.py - Test: tests/unit/test_escalation.py - Test: tests/unit/test_audit.py

    Implementation guidance:

    approval.py -- Approval gate middleware: - ApprovalGate class with async def request_approval(action, context, confidence) -> ApprovalDecision - ApprovalDecision enum: APPROVED, REJECTED, MODIFIED, TIMED_OUT - ApprovalPolicy: configurable per-action rules (auto-approve above threshold, always-require for write/delete, time-boxed auto-approve) - MockApprovalProvider for testing (returns configured decisions) - ConsoleApprovalProvider for interactive use (prompts user on stdin)

    escalation.py -- Escalation policy engine: - EscalationPolicy class with rules: confidence thresholds, risk tiers (low/medium/high/critical), max-autonomous-actions-before-review - EscalationDecision: PROCEED, ESCALATE, HALT - evaluate(action, confidence, risk_tier) -> EscalationDecision - Configurable: different thresholds per risk tier

    audit.py -- Structured audit logging: - AuditLog class that records every decision (human and agent) - AuditEntry model: timestamp, actor (human/agent), action, decision, confidence, approval_status, context - to_json(), to_markdown() for export - Append-only design (entries cannot be modified after creation)

    Tests should verify: - Approval gate honors auto-approve thresholds - Approval gate requires human review for write actions - Escalation policy returns correct decision for each risk tier - Audit log records entries and cannot be modified - Audit log exports to JSON and markdown

    Implementation guidance:

    src/signals.py -- Simulated alert/metric ingestion: - Alert model: alert_id, severity (info/warning/error/critical), source, message, timestamp, metrics - generate_incidents() function returning a list of simulated incidents (10-15 predefined scenarios: CPU spike, disk full, memory leak, service timeout, error rate spike, certificate expiring, database connection pool exhaustion, etc.)

    src/runbook_search.py -- Runbook retrieval: - Runbook model: id, title, symptoms, steps (list of remediation steps), risk_level, requires_approval - RunbookIndex class using ChromaDB (same pattern as DocumentIndex) - Ships with 10-15 predefined runbooks matching the simulated incidents

    src/remediation.py -- Remediation proposal engine: - RemediationProposal model: runbook_id, proposed_steps, confidence, risk_level, requires_approval - Uses ModelClient to match alerts to runbooks and propose specific remediation - Confidence scoring based on symptom match quality

    src/agent.py -- The agent loop with approval gates: - IncidentRunbookAgent class - Loop: receive alert -> search runbooks -> propose remediation -> request approval (if required) -> execute (or dry-run) -> log audit trail - Uses ApprovalGate from src/ch05_hitl/approval.py - Uses EscalationPolicy from src/ch05_hitl/escalation.py - Uses AuditLog from src/ch05_hitl/audit.py - Has dry_run mode (propose only, never execute)

    evals/dataset.jsonl -- 25 incident scenarios with expected triage, expected runbook match, expected escalation behavior.

    docs/failure-analysis.md -- Failure surfaces: false alert matching, runbook gap (no matching procedure), over-escalation, under-escalation, audit gaps.
