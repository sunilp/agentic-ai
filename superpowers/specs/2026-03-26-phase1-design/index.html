    Agentic AI for Serious Engineers -- Phase 1 Design Spec¶

    Version: 1.0 Date: 2026-03-26 Status: Approved Owner: Sunil Prakash

    1. Identity and Positioning¶

    1.1 Title¶

    Agentic AI for Serious Engineers

    1.2 Subtitle¶

    A practical field guide to building reliable, evaluable, and production-grade agent systems

    1.3 Opening statement¶

    "Most agentic AI material teaches you how to make an impressive demo. This repo teaches engineers how to build agent systems that survive real-world constraints."

    1.4 Core thesis¶

    Before you build an agent, you need to understand what an agent actually is, why it behaves the way it does, what makes it different from the systems you already know, and where the failure surfaces are. Only then does "how to build one" become useful. This repo teaches the why and what first, then the how, then the judgment to know when not to.

    1.5 Audience¶

    Primary: - Backend engineers, platform engineers, staff+ engineers, software architects, technical leads, data engineers moving into AI, engineers building internal AI platforms

    Assumed baseline: APIs, Python, software architecture, services and interfaces, testing, databases, production systems at a general level.

    Not assumed: Transformers in depth, embeddings and retrieval, agent orchestration, AI evaluation, agent governance.

    Not for: Complete beginners to programming, prompt-engineering-only learners, people looking for a framework tutorial or a crash course.

    1.6 Voice¶

    Calm, precise, opinionated, technically mature, practical. Written by someone who has seen systems break. No hype, no "agents will change everything," no framework tribalism.

    1.7 Relationship to "The Enterprise AI Operating System" (book)¶

    This repo is the hands-on engineering layer. The book covers enterprise strategy, operating model, governance, and organizational design. The repo covers building, evaluating, and hardening agent systems. They complement each other. A bridge chapter connecting the two arrives in Phase 2, not Phase 1. The repo stands alone -- no book required.

    2. Learning Philosophy¶

    These five principles define how every chapter is structured and what makes this repo different from tutorials and framework docs.

    2.1 Why before how¶

    Every topic starts with the engineering reason it matters. Not "here's the API," but "here's the problem this solves and why you should care."

    2.2 What breaks before what works¶

    Failure modes are first-class, not an afterthought section at the bottom. Engineers learn fastest when they understand what can go wrong.

    2.3 Compare alternatives¶

    Every design choice is framed against what you would do instead. Workflow vs agent, single vs multi, cheap model vs expensive, planner vs direct. No decision is presented in isolation.

    2.4 Build, inspect, harden¶

    Each system goes through: baseline implementation, improved version, instrumentation, evaluation, hardening. This mirrors how real production engineering works.

    2.5 Teach transferable judgment¶

    Concepts that survive tool and framework churn. An engineer who reads this should make better decisions regardless of which SDK they use next year.

    3. Content Architecture¶

    3.1 Three layers¶

    Layer 1: Field manual chapters. Structured markdown that teaches concepts, tradeoffs, and design patterns. The why and what.

    Layer 2: Working examples. Runnable per-chapter code that makes concepts concrete. The how.

    Layer 3: Threaded project. One end-to-end system (Document Intelligence Agent) built incrementally across all chapters. The proof.

    3.2 Narrative spine¶

    The Document Intelligence Agent is introduced in Chapter 1, first built in Chapter 2, compared against a workflow in Chapter 3, evaluated and hardened in Chapter 4, and honestly assessed in Chapter 5. It is the vehicle for learning, not a separate section.

    3.3 Curiosity-driven flow¶

    Each chapter ends with a question the reader can't help but ask, and the next chapter answers it. Not artificial cliffhangers -- genuine engineering curiosity that flows from what they just learned.

    4. Chapter Design¶

    4.1 Chapter template¶

    Every chapter follows this structure:

    1. Why this matters -- connect to real engineering value
    2. Core concepts -- minimal theory, rigorously explained
    3. Design guidance -- how to structure the solution well
    4. Failure modes -- what breaks and why, woven throughout
    5. Working example -- runnable code, building on the threaded project
    6. Evaluation -- how to know it works
    7. Production notes -- cost, reliability, security, governance
    8. Further reading -- short list, high-signal only

    4.2 Chapter 1: What "agentic" actually means¶

    Purpose: Disambiguate the core term. Give engineers a precise vocabulary before they build anything.

    Topics: - LLM app vs workflow vs tool-using system vs agent vs multi-agent - Bounded autonomy and action spaces - Stateful decision loops - What is NOT an agent (most things people call agents)

    Deliverables: - Comparison table: five system types with characteristics - Decision map: which pattern for which problem shape - Introduction of the Document Intelligence Agent as the running example

    Plants the question: "I understand the concepts. But what does an LLM actually need to know and do to become useful inside a system?"

    4.3 Chapter 2: Tools, context, and the agent loop¶

    Purpose: Teach the building blocks that make an agent functional. Start building.

    Topics: - Brief LLM primer for engineers: context windows, structured outputs, stochasticity, and why these properties matter for system design (enough to build, not a full ML chapter) - Tools as contracts: schema design, argument validation, side-effect categories (read vs write), permission scopes, retries, result normalization - Context engineering: system prompts, task prompts, retrieval context, grounding, relevance filtering, context packing, prompt injection boundaries - The observe-think-act loop: how tools + context + reasoning form the basic agent cycle

    Code deliverables: - Tool registry with validation and error handling - Document loader, chunker, retriever, extractor tools - Context assembly pipeline - First working Document Intelligence Agent: query in, cited answer out

    Plants the question: "I can build a tool-using loop. But when should this be a deterministic workflow instead? When does it actually need autonomy?"

    4.4 Chapter 3: Workflow-first, agent-second¶

    Purpose: Teach the most important architectural decision: when to use a workflow, when to use an agent, and how to build each well.

    Topics: - Deterministic orchestration vs bounded autonomy -- when each wins - Same document intelligence task implemented as workflow AND as agent, side by side - Single-agent design: iteration budgets, stop conditions, uncertainty handling, graceful degradation - State and memory: session state, task state, working memory -- introduced here because they only matter once you have chosen the agent path - Planning and decomposition: direct response vs plan-and-execute, reflection loops

    Code deliverables: - Workflow implementation of the Document Intelligence Agent - Agent implementation with bounded autonomy - Side-by-side comparison runner - State management and uncertainty-based escalation

    Plants the question: "I've built it both ways. But how do I know if it actually works? And what happens when it doesn't?"

    4.5 Chapter 4: Evaluating and hardening agent systems¶

    Purpose: Make the system trustworthy. If you can't evaluate it, you don't understand it well enough to ship it.

    Topics: - Evaluation: task-level evals, rubric scoring, judge models, regression tests, adversarial cases, failure bucketing - Observability: traces, tool logs, state inspection, token accounting, latency decomposition, replay - Reliability: retries, backoff, idempotency, timeout handling, checkpointing, crash recovery - Cost and latency: model routing, caching, batching, budget-aware orchestration - Security: prompt injection, malicious retrieved content, tool abuse, data exfiltration, least privilege, policy enforcement outside model context

    Code deliverables: - Eval harness for the Document Intelligence Agent (gold dataset, rubric, comparison script, baseline report) - Trace logging and structured failure diagnosis - Reliability hardening (retry, checkpoint, resume-after-crash) - Cost profiling across model tiers - Attack simulation and mitigations

    Plants the question: "I can build, evaluate, and harden an agent. But are there times I shouldn't build one at all?"

    4.6 Chapter 5: When not to use agents¶

    Purpose: The signature chapter. Teach judgment.

    Topics: - Workflow-first alternatives - Rules engines - Retrieval-only systems - Classifiers - Simpler architectures that win - Decision framework: when autonomy adds value vs when it adds risk - Cost of autonomy vs value of autonomy - Real examples of systems built as agents that should not have been - Honest retrospective on the Document Intelligence Agent: which parts actually needed agent autonomy? Which parts should have stayed as workflows?

    Deliverables: - Decision framework (when to use what) - Retrospective analysis of the threaded project

    This chapter should be one of the strongest in the repo. It is what makes the repo credible. Anyone can teach you to build agents. Teaching you when NOT to is the judgment that matters.

    5. Document Intelligence Agent -- Project Design¶

    5.1 What it does¶

    • Ingests documents (PDF, markdown, text)
    • Chunks and indexes content
    • Retrieves evidence for questions
    • Answers with citations and structured extraction
    • Escalates on uncertainty (does not hallucinate an answer when it does not know)

    5.2 Why this project¶

    • Naturally teaches retrieval, grounding, structured outputs, tool design, evaluation, and uncertainty handling
    • Real engineering problem every company has
    • Complex enough to be interesting, bounded enough to finish
    • Clear, measurable success criteria (did it cite the right source? did it extract correctly?)

    5.3 How it evolves through the chapters¶

    Chapter What gets built
    Ch 1 Project introduced as the running example. Concepts from the chapter are mapped to what the system will need.
    Ch 2 Tool registry (document loader, chunker, retriever, extractor). Context assembly pipeline. First working version: query in, cited answer out.
    Ch 3 Same task as workflow and as agent, side by side. State management, planning, uncertainty-based escalation added.
    Ch 4 Eval harness (gold dataset, rubrics, failure buckets). Trace logging. Reliability hardening. Cost profiling. Security pass.
    Ch 5 Retrospective: which parts needed agent autonomy, which should have been workflows. Honest assessment.

    5.4 Eval harness¶

    Ships with Phase 1: - Gold dataset: 30-50 question/answer pairs with source citations - Rubric: correctness, groundedness, citation accuracy, extraction quality, uncertainty handling - Comparison script: run eval, produce scored report - Baseline report: how the system performs out of the box - Failure buckets: categorized failure types with examples

    7. Code Standards¶

    7.1 Language and stack¶

    • Python (primary)
    • FastAPI, Pydantic, asyncio, pytest
    • PostgreSQL or SQLite for state/storage
    • Provider-neutral model client (not locked to one LLM vendor)
    • Basic Docker support

    7.2 Code philosophy¶

    • Clean, modular, typed where practical
    • Small enough to understand, realistic enough to matter
    • Runnable with minimal friction (make run, make test, make eval)
    • No giant opaque notebooks, no magic-heavy framework wrappers

    7.3 Three implementation styles¶

    Where instructive, examples appear in three styles: 1. Raw API implementation 2. Minimal custom orchestration 3. Selected framework implementation

    This teaches the concept, not one vendor's ecosystem.

    8. Diagrams¶

    8.1 Required for Phase 1¶

    • System architecture diagram (Document Intelligence Agent)
    • Execution flow: workflow vs agent comparison
    • Trust boundary diagram
    • Failure surface diagram
    • Evaluation loop diagram

    8.2 Quality bar¶

    Architecture-grade. Clean, professional, useful for reference. Not napkin sketches.

    9. Phase 1 Deliverables Summary¶

    PRINCIPLES.md 6-8 principles: why before how, concept over framework, evaluation mandatory, no hype, security outside the model, explicit tradeoffs.
    ROADMAP.md What shipped, what is next. Honest about scope.
    5 chapters Fully written, each following the standard template.

    10. Phase 2 and Beyond (Sketch)¶

    Phase 2 and 3 are not committed. They are directions, not promises.

    Phase 2 -- Architecture and Production depth: - Multi-agent systems without theater - State graphs and orchestration - Human-in-the-loop as architecture - Deeper security chapter (standalone) - Governance and auditability - Bridge chapter: how agent systems fit into enterprise operating models (connects to book) - 2 more end-to-end projects (Codebase Analyst, Incident Runbook Agent)

    Phase 3 -- Advanced: - Protocols and interoperability - Durable execution - Advanced memory systems - Evaluation at scale - Remaining projects (Data Analyst Agent, Policy Controls Agent, Multi-Agent Research System)

    Content ships when it meets the quality bar. The roadmap shows these phases exist but does not commit to timelines.

    11. Success Criteria¶

    Phase 1 succeeds if: - A strong engineer reads it and feels smarter, more careful, and more capable - The repo is shared as a serious engineering reference, not a demo showcase - Readers can move from basic LLM app building to structured agent systems thinking - The examples are seen as practical and disciplined - The eval harness produces a real report with real numbers - The "when not to use agents" chapter gets cited independently

    The quality test: Would a staff engineer recommend this to their team?
