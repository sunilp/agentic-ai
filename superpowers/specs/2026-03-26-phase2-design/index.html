    Agentic AI for Serious Engineers -- Phase 2 Design Spec¶

    Version: 1.0 Date: 2026-03-26 Status: Approved Owner: Sunil Prakash Depends on: Phase 1 (complete)

    1. Overview¶

    Phase 2 transforms the repo from a GitHub-native markdown project into a polished open book with a dedicated reading experience, two new chapters, and a second end-to-end project. The goal is to make the repo public-ready: something an engineer bookmarks, shares with their team, and returns to as a reference.

    1.1 What ships in Phase 2¶

    • MkDocs Material site deployed to sunilprakash.com/agentic-ai/
    • Chapter 4: Multi-Agent Systems Without Theater (new)
    • Chapter 5: Human-in-the-Loop as Architecture (new)
    • Multi-agent extension to the Document Intelligence Agent
    • Incident Runbook Agent (second end-to-end project with eval harness)
    • Updated Chapter 7 (When Not to Use Agents) expanded to cover multi-agent and HITL tradeoffs
    • "Books" section added to sunilprakash.com
    • README updated to point to the live site

    1.2 What does not ship in Phase 2¶

    • State graphs and orchestration chapter (Phase 3)
    • Standalone security chapter (Phase 3)
    • Governance and auditability chapter (Phase 3)
    • Enterprise bridge chapter (Phase 3)
    • Advanced topics: protocols, durable execution, advanced memory, eval at scale (Phase 3+)

    3.2 Chapter 4: Multi-Agent Systems Without Theater¶

    Purpose: Teach when multi-agent is justified and what it looks like done right, vs when it's complexity theater.

    Position in flow: After "Workflow-First, Agent-Second." The question from Chapter 3: "I know when to use a single agent. But when do I actually need multiple?"

    Topics: - When multi-agent is justified: specialization (different tools/knowledge), verification (independent checks), decomposition (subtasks requiring different reasoning) - When multi-agent is theater: adding agents for org-chart reasons, splitting a simple task across roles that don't need separation, using three agents where one with tools would suffice - Patterns: coordinator-worker, critic-proposer, reviewer chains - Coordination overhead: shared state management, message contracts between agents, merge conflicts when agents disagree, loop detection, stopping rules - Cost explosion: multi-agent multiplies the agent tax (2-5x more tokens, 3-10x more latency, harder debugging) - Threaded project extension: multi-agent mode for the Document Intelligence Agent

    Threaded project extension: - Add a multi-agent mode: retriever agent (searches and retrieves), reasoning agent (synthesizes answer from evidence), verifier agent (checks citations against sources) - Same task as Chapter 2-3, now with role decomposition - Side-by-side comparison: single-agent vs multi-agent on the same eval dataset - Honest assessment: does multi-agent actually improve quality enough to justify the cost for this task?

    Code deliverables (src/ch04_multiagent/): - orchestrator.py -- multi-agent coordinator (dispatches tasks, collects results, manages flow) - agents.py -- role-based agent definitions (RetrieverAgent, ReasoningAgent, VerifierAgent) - contracts.py -- message types and contracts between agents - compare.py -- comparison runner: single-agent vs multi-agent on same queries - run.py -- CLI entry point

    Plants the question: "If agents can be wrong and multi-agent is expensive, how do I keep a human in the loop without killing the automation value?"

    3.3 Chapter 5: Human-in-the-Loop as Architecture¶

    Purpose: Teach HITL as a first-class architectural decision, not a band-aid.

    Position in flow: After multi-agent. The question from Chapter 4: readers now understand the cost of autonomy and need to know how to add human oversight without destroying the value.

    Topics: - HITL is architecture, not a patch -- it should be designed in, not bolted on after something breaks - Approval stages: pre-action approval, post-action review, time-boxed auto-approve - Escalation patterns: confidence-gated escalation, policy-based escalation, anomaly-based escalation - Uncertainty thresholds: when to ask vs when to act (configurable per-action, per-risk-level) - Reviewer interaction models: async approval queues, real-time approval, batch review - Auditability: every decision (human and agent) has a trail - Cost of HITL: latency increase, staffing requirements, queue management - When HITL adds value vs when it's security theater

    New project: Incident Runbook Agent - Inspects system signals (simulated alerts, metrics, log patterns) - Searches runbooks for matching procedures - Proposes remediation steps with confidence scores - Requests human approval before executing any action - Logs everything with full audit trail - Has a "dry run" mode (propose only, never execute)

    Code deliverables (src/ch05_hitl/): - approval.py -- approval gate middleware (sync and async approval flows) - escalation.py -- escalation policy engine (confidence thresholds, risk tiers, auto-approve rules) - audit.py -- structured audit logging (every decision, human and agent)

    Project deliverables (project/incident-runbook-agent/): - src/ -- runbook agent with HITL architecture - signals.py -- simulated alert/metric ingestion - runbook_search.py -- runbook retrieval and matching - remediation.py -- remediation proposal engine - agent.py -- the agent loop with approval gates - run.py -- CLI entry point - tests/ -- unit and integration tests - evals/ -- eval dataset (20-30 incident scenarios), rubric, runner - Test categories: correct triage, appropriate escalation, unnecessary escalation, missed escalation, audit completeness - docs/architecture.md -- system design - docs/failure-analysis.md -- failure surfaces and mitigations

    Plants the question: "I can build, extend, and govern agent systems. But how do I know they actually work in production? And how do I keep them working?"

    3.4 Chapter 7 expansion (When Not to Use Agents)¶

    The existing Chapter 5 (renumbered to 7) gets expanded to include: - Multi-agent anti-patterns from Chapter 4 (systems that used 3 agents where 1 would suffice) - HITL cost analysis (when the human overhead exceeds the automation value) - Updated retrospective on the Document Intelligence Agent covering single-agent, multi-agent, and HITL variants - Updated decision framework incorporating the full spectrum: workflow -> single agent -> multi-agent -> HITL agent

    8. Phase 3 and Beyond (Sketch)¶

    Directions, not promises. Recorded here for planning continuity.

    Phase 3 -- Architecture Depth: - State graphs and orchestration (DAGs, checkpoints, resumability) - Deeper security chapter (standalone, expanded from Phase 1 security module) - Governance and auditability (decision logs, trace retention, compliance patterns) - Bridge chapter: how agent systems fit into enterprise operating models (connects to the book) - 1-2 more projects: Data Analyst Agent, Codebase Analyst

    Phase 4 -- Advanced: - Protocols and interoperability (tool contracts, capability declarations, session boundaries) - Durable execution (checkpoints, replay, fault recovery) - Advanced memory systems (memory distillation, lifecycle management, trust) - Evaluation at scale (synthetic data, benchmark versioning, drift detection) - Policy Controls Agent, Multi-Agent Research System

    Publisher strategy: - Open-source repo + site builds audience and validates content - Pitch publishers (Manning, O'Reilly) with traction data after public launch - Published book is an expanded, edited edition -- not a replacement for the open version - Open version drives traffic; published version adds credibility and revenue

    9. Success Criteria¶

    Phase 2 succeeds if: - The site is a genuinely good reading experience (not just "rendered markdown") - A staff engineer reads Chapters 4 and 5 and feels the multi-agent and HITL guidance fills a real gap - The Incident Runbook Agent is a compelling second project that feels like a different domain from document intelligence - The repo has two projects, seven chapters, 50+ tests, and feels like a reference, not a tutorial - Someone can share the URL sunilprakash.com/agentic-ai/ and the recipient immediately understands what it is

    The quality test: Would an engineering manager send this link to their team with the note "Read this before you build any agent system"?
